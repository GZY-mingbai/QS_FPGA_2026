# GB2312 点阵字库格式说明

本文档描述 `font_gb2312.bin` 的文件格式。该字库面向 FPGA 使用，**扁平、无压缩、无表头**，
任何字形的字节偏移都可以用一条公式直接算出，适合按「地址 + 长度」裸读
（正好配合工程里的 `src/user_source/hdl_source/spi_flash_read.v`）。

**全部字形统一为 16×16 / 32 字节**，文件里只有一种步进值，FPGA 侧不需要按尺寸分支。

| 项目 | 值 |
|---|---|
| 文件名 | `font_gb2312.bin` |
| 文件大小 | **247,744 字节**（241.94 KiB，`0x3C7C0`） |
| SHA-256 | `1cae592f8c1bf61527c5f6bae277ecdf7629a6c2207d0b2087d892f0b8c57948` |
| ASCII 来源 | `ascii.png`（8×8，2 倍放大到 16×16） |
| 汉字/符号来源 | `unifont-17.0.01.bmp`（16×16） |
| 覆盖范围 | ASCII 0x21–0x7E + GB2312 全部 7445 个字符 |
| 压缩 | **无**（刻意不用，避免 FPGA 解压逻辑） |
| 字节序 | 小端无关（纯字节流，逐字节存放） |

---

## 1. 总体布局

文件由两个连续块组成，中间没有任何分隔符或填充：

| 块 | 起始偏移 | 内容 | 单元大小 | 字形数 | 占用 |
|---|---|---|---|---|---|
| **块 0** | `0x000000` | ASCII | 32 字节 | 128 | 4,096 字节 |
| **块 1** | `0x001000` | GB2312 | 32 字节 | 81 区 × 94 位 = 7,614 | 243,648 字节 |
| | | | | **合计** | **247,744 字节** |

```
偏移 0x000000        0x001000                                                          0x03C7C0
      ├────────────────┬──────────────────────────────────────────────────────────────────┤
      │  块0 ASCII      │  块1 GB2312                                                       │
      │  128 × 32 B     │  81 行 × 94 列 × 32 B                                              │
      │  = 4096 B       │  = 243648 B                                                       │
      └────────────────┴──────────────────────────────────────────────────────────────────┘
        ← 两个块步进都是 32 字节，取字形的代码路径完全一致 →
```

## 2. 块 0 —— ASCII（16×16）

### 2.1 为什么是 16×16

源图 `ascii.png` 里 ASCII 是 **8×8**。为了和汉字块统一尺寸，生成时做了
**2 倍最近邻放大**：一个源像素 → 2×2 目标像素。

- 放大后字形形状完全不变，点阵保持锐利，**不引入任何插值灰阶**
- 好处：整个字库只有一种字形尺寸、一种字节步进，渲染器不用判断分支

### 2.2 寻址

覆盖 `0x00`–`0x7F`，**一律按 128 项排布**，寻址不需要任何减法或分支：

```
偏移 = 字符编码 × 32           // 编码范围 0x00 ~ 0x7F
```

| 编码 | 内容 | 偏移 |
|---|---|---|
| `0x00`–`0x1F` | 全 0（空白） | `0x0000`–`0x03FF` |
| `0x20` 空格 | 全 0（空白） | `0x0400` |
| `0x21`–`0x7E` | 来自 `ascii.png`，放大 2 倍 | `0x0420`–`0x0FC0` |
| `0x7F` | 全 0（空白） | `0x0FE0` |

> 控制符与空格都留空（32 个 `0x00`），因此 FPGA 拿到任何 `< 0x80` 的字节都可以放心寻址，
> 不需要预先判断是不是可打印字符。

### 2.3 位序与字节序

与汉字块**完全一致**：每字形 32 字节，按行自上而下，每行 2 字节（先左半 8 列，再右半 8 列）。
每个字节 **bit7 = 该 8 列中最左边像素**，**bit = 1 表示点亮**。

### 2.4 示例：字符 `A`（0x41）

偏移 = `0x41 × 32` = 2080（`0x820`）

| 偏移 | 字节 | 点阵（16 列） |
|---|---|---|
| 0x820 | `3F 00` | `..######........` |
| 0x822 | `3F 00` | `..######........` |
| 0x824 | `C0 C0` | `##......##......` |
| 0x826 | `C0 C0` | `##......##......` |
| 0x828 | `FF C0` | `##########......` |
| 0x82A | `FF C0` | `##########......` |
| 0x82C | `C0 C0` | `##......##......` |
| 0x82E | `C0 C0` | `##......##......` |
| 0x830 | `C0 C0` | `##......##......` |
| 0x832 | `C0 C0` | `##......##......` |
| 0x834 | `C0 C0` | `##......##......` |

> ⚠️ **注意字形偏左**：源图 `ascii.png` 的字形在 8 列格内是**左对齐**的（笔画约占左侧 5–6 列），
> 放大 2 倍后仍然偏左 —— 上面 `A` 只用了第 0–9 列，右侧留 6 列空白。
> 这是原图自带的风格，字库**默认原样保留**。

> ```
>
> 如果用 **8 px 半宽排版**，保持默认 `0` 即可。

## 3. 块 1 —— GB2312（16×16）

### 3.1 行号映射（关键）

GB2312 有 94 个区，但只有 81 个区有内容。**空区（区 10–15、区 88–94）不占空间**，
用「行号」重新编号：

| GB2312 区 | 区码 `qb` | 行号 `row` | 数量 |
|---|---|---|---|
| 区 1–9（符号区） | `0xA1`–`0xA9` | `0`–`8` | 9 行 |
| 区 10–15（空） | `0xAA`–`0xAF` | — | **不存储** |
| 区 16–87（汉字区） | `0xB0`–`0xF7` | `9`–`80` | 72 行 |
| 区 88–94（空） | `0xF8`–`0xFE` | — | **不存储** |

```
row = (qb <= 0xA9) ? (qb - 0xA1) : (qb - 0xB0 + 9)
```

| 区 | 内容 | 字符数 |
|---|---|---|
| 1 | 标点符号 | 94 |
| 2 | 数字/序号 | 72 |
| 3 | 全角拉丁字母 | 94 |
| 4 | 平假名 | 83 |
| 5 | 片假名 | 86 |
| 6 | 希腊字母 | 48 |
| 7 | 西里尔字母 | 66 |
| 8 | 拼音/注音 | 63 |
| 9 | 制表符 | 76 |
| | **符号区小计** | **682** |
| 16–55 | 一级汉字（按拼音序） | 3755 |
| 56–87 | 二级汉字（按部首序） | 3008 |
| | **总计** | **7445** |

### 3.2 寻址

```
偏移 = 0x1000 + (row × 94 + (wb - 0xA1)) × 32
```

其中 `wb` 是位码（`0xA1`–`0xFE`），`位 = wb - 0xA0`。

展开成一步到位的式子（省掉中间变量）：

```
偏移 = 0x1000 + (row × 3008) + ((wb - 0xA1) × 32)
```

> 一次取 32 字节即可得到完整字形，对应 `spi_flash_read.v` 的 `rd_len = 32`。

### 3.3 位序与字节序

每字形 **32 字节**，按行自上而下，**每行占 2 字节**（先左半 8 列，再右半 8 列）：

```
        行0  → byte[0] (列0-7) , byte[1] (列8-15)
        行1  → byte[2] (列0-7) , byte[3] (列8-15)
        ...
        行15 → byte[30](列0-7) , byte[31](列8-15)
```

每个字节 **bit7 = 该 8 列中最左边像素**，**bit = 1 表示点亮**。
这就是通行的 HZK16 格式，绝大多数汉字取模软件与字库芯片都是这个约定。

### 3.4 示例：汉字 `中`（`0xD6 0xD0`）

区 = `0xD6 - 0xA0` = 54，位 = `0xD0 - 0xA0` = 48
`row = 0xD6 - 0xB0 + 9 = 47`
偏移 = `0x1000 + (47 × 94 + 47) × 32` = **146,976**（`0x023E20`）

| 偏移 | 字节 | 点阵（16 列） |
|---|---|---|
| 0x23E20 | `01 00` | `.......#........` |
| 0x23E22 | `01 00` | `.......#........` |
| 0x23E24 | `01 00` | `.......#........` |
| 0x23E26 | `01 00` | `.......#........` |
| 0x23E28 | `3F F8` | `..###########...` |
| 0x23E2A | `21 08` | `..#....#....#...` |
| 0x23E2C | `21 08` | `..#....#....#...` |
| 0x23E2E | `21 08` | `..#....#....#...` |
| 0x23E30 | `21 08` | `..#....#....#...` |
| 0x23E32 | `21 08` | `..#....#....#...` |
| 0x23E34 | `3F F8` | `..###########...` |
| 0x23E36 | `21 08` | `..#....#....#...` |
| 0x23E38 | `01 00` | `.......#........` |
| 0x23E3A | `01 00` | `.......#........` |
| 0x23E3C | `01 00` | `.......#........` |
| 0x23E3E | `01 00` | `.......#........` |

### 3.5 未定义码位

GB2312 在已使用的 81 个区里仍有 **169 个位置未定义**（例如区 2 的 `0xA2A1`）。
这些位置**全部填 0**（32 个 `0x00`），保证渲染结果是空白而不是乱码。

```
偏移 = 0x1000 + (row × 94 + (wb - 0xA1)) × 32     // 未定义位：整块 0x00
```

## 4. Verilog 读取示例

```verilog
//------------------------------------------------------------------
//  字库布局常量（与 font_gb2312.bin 一一对应）
//------------------------------------------------------------------
localparam [23:0] ASCII_BASE = 24'h000000;
localparam [23:0] GB_BASE    = 24'h001000;
localparam        GB_COLS    = 94;          // 每区 94 位
localparam        GLYPH_BYTES = 32;         // 所有字形统一 32 字节

//------------------------------------------------------------------
//  单字节 ASCII → Flash 地址（byte0 < 0x80 时使用）
//------------------------------------------------------------------
wire [23:0] ascii_addr = ASCII_BASE + {16'd0, byte0} * GLYPH_BYTES;

//------------------------------------------------------------------
//  GB2312 双字节 → Flash 地址（byte0 >= 0x80 时使用）
//------------------------------------------------------------------
function [23:0] gb_addr;
    input [7:0] qb;                 // 区码 0xA1~0xF7
    input [7:0] wb;                 // 位码 0xA1~0xFE
    reg  [15:0] row;
    begin
        // 区 1..9 → row 0..8 ；区 16..87 → row 9..80 ；其余区不存储
        row     = (qb <= 8'hA9) ? ({8'd0, qb} - 16'h00A1)
                                : ({8'd0, qb} - 16'h00B0 + 16'd9);
        gb_addr = GB_BASE + (row * GB_COLS + ({8'd0, wb} - 16'h00A1)) * GLYPH_BYTES;
    end
endfunction

//------------------------------------------------------------------
//  取字形：一次请求读 32 字节（ASCII 与汉字路径完全一样）
//------------------------------------------------------------------
//  wire [23:0] glyph_addr = (byte0 < 8'h80) ? ascii_addr : gb_addr(byte0, byte1);
//
//  spi_flash_read #(...) u_flash (
//      .rd_addr (glyph_addr),      // 24bit
//      .rd_len  (16'd32),          // 恒定 32 字节
//      ...
//  );
//  读回后：bytes[2*r] = 第 r 行左 8 列，bytes[2*r+1] = 第 r 行右 8 列
//          bit7 是最左像素，bit=1 点亮
```

> `row * 94 * 32` 里的乘法是常数乘法，综合工具会自动转成移位相加
> （`3008 = 2048 + 512 + 256 + 128 + 64`），不消耗 DSP。

## 5. 与 `spi_flash_read.v` 配合

工程里已有 `src/user_source/hdl_source/spi_flash_read.v`，本字库可直接烧进 W25Q64 使用：

| 项目 | 说明 |
|---|---|
| 建议烧写地址 | `0x000000`（字库自身无表头，整块占用 `0x000000`–`0x03C7BF`） |
| Flash 容量 | W25Q64 = 8 MB，字库仅占 0.24 MB，余量充足 |
| 单次读长度 | **恒定 32 字节**，远小于 `rd_len` 上限 65535 |
| 跨页 | 读命令（`03h`）可自由跨 256 字节页边界，无需对齐 |
| 速度 | SCLK = 12.5 MHz 时约 1.5 MB/s；**实时显示请先整块读进 SDRAM**（见该文件注释） |

## 6. 渲染时的注意事项

1. **尺寸统一**：所有字形都是 16×16 / 32 字节，渲染器不需要按尺寸分支。
2. **分流规则**：字节值 `< 0x80` 走块 0（ASCII），`>= 0x80` 与后一字节组成 GB2312 走块 1。
3. **步进宽度**：汉字必须 16 px 步进。ASCII 可 16 px 等宽步进
   （此时建议按 2.4 节加 `--ascii-shift-x 2`），也可 8 px 半宽步进。
4. **bit = 1 表示点亮**。若驱动的是「低电平点亮」的 OLED，取反即可。
5. **ASCII 笔画偏细**：2 倍最近邻放大后，ASCII 的笔画宽度是汉字的一半左右，
   视觉上会比汉字「细」。这是放大方式决定的，若希望等粗需要另做加粗处理。

## 7. 为什么这么设计

### 为什么不用压缩

用户明确要求「不要压缩算法」。压缩（RLE、字典）需要额外的解压状态机，
而字库本身只有 242 KiB，对 8 MB Flash 而言占比 3%，压缩省下的空间换不回逻辑复杂度。
无压缩 → FPGA 侧只需一个地址加法器 + 一个字节计数器。

### 为什么 ASCII 放大到 16×16

如果 ASCII 保持 8×8，文件里就存在两种尺寸（8 字节 / 32 字节两种步进），
渲染器要分两条代码路径，取字形的地址计算也多一层判断。
统一成 16×16 后：

- 只有一个步进常量 `32`，ASCII 与汉字共用同一套读取逻辑
- 文件只增加 3,072 字节（从 1,024 → 4,096 字节），代价极小
- 混合排版时两者基线天然对齐

### 为什么跳过空区

如果按完整的 94 区 × 94 位存储，需要 `94 × 94 × 32 = 282,752` 字节；
跳过空的区 10–15、88–94 后只需 `81 × 94 × 32 = 243,648` 字节，**省下 39,104 字节（13.8%）**。
代价只是寻址公式多一个比较器（见 3.1 节），非常划算。

若希望寻址公式**零分支**（连比较器都不要），可改为完整 94 区存储，
公式退化为 `偏移 = 0x1000 + ((qb - 0xA1) × 94 + (wb - 0xA1)) × 32`，
文件大小变为 286,848 字节。需要这个版本的话改 `gen_font.py` 里的 `GB_ROWS` 即可。

### 为什么 ASCII 按 128 项而不是 94 项

按 128 项排布，寻址就是一次「× 32」的移位，不需要减去 `0x21`。
多占的空白项（0x00–0x1F、0x20、0x7F 共 33 个）只有 1,056 字节，完全可以忽略。

## 8. 生成与校验

### 重新生成

```bash
pip install pillow
cd Font
python gen_font.py
```

可选参数：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--ascii` | `ascii.png` | ASCII 源图 |
| `--unifont` | `unifont-17.0.01.bmp` | 汉字源图 |
| `--out` | `font_gb2312.bin` | 输出字库 |
| `--preview` | `font_preview.png` | 抽样预览图 |
| `--ascii-shift-x` | `0` | ASCII 放大后整体右移像素数（0–8），等宽排版可用 `2` |

> 改过 `--ascii-shift-x` 后，`verify_font.py` 顶部的 `ASCII_SHIFT_X` 也要同步改，否则校验会报不一致。

### 校验

```bash
python verify_font.py
```

校验脚本用**完全独立的提取路径**（PIL `crop` 而非 `tobytes` 索引）重新从源图取点阵，
与按本文档公式从 `.bin` 里寻址取出的数据**逐字节比对**：

```
bin 大小: 247744 字节
ASCII 0x21~0x7E : 94/94 一致
ASCII 保留位全 0 : 是
GB2312 全量比对 : 7445 个字形，0 个不一致
未定义位全 0    : 是 (0 个异常)
随机抽样 30 ASCII: 全部一致
------------------------------------------------------------
校验通过：bin 与源图逐字节一致
```

同时输出 `font_sample.png`（ASCII + 中文混排样张，可直接肉眼确认）。

## 9. 源图规格备忘（踩过的坑）

生成脚本依赖以下实测参数，改动源图前务必先确认：

### `ascii.png`

| 项目 | 值 |
|---|---|
| 尺寸 | 128 × 128 |
| 颜色模式 | **P（调色板）** |
| ⚠️ 陷阱 | **调色板是坏的**——所有调色板项 RGB 都是白色，`convert("L")` / `convert("RGB")` 会得到一张纯白图 |
| ✅ 正确读法 | 必须读**原始调色板索引**（`Image.getdata()`），`索引 1 = 笔画`，`索引 0 = 背景` |
| 网格 | 单元格 8×8，横向 16 格、纵向 6 格 |
| 起始位置 | 首行点阵从 **y = 16** 开始（顶部 16 行是留白） |
| 字形风格 | 格内**左上对齐**，笔画约占左侧 5–6 列、上方 7 行 |
| 图像下半部 | y=64 以下还有一批 GB2312 符号区字形，**本字库不使用**（符号区统一走 `unifont`） |

### `unifont-17.0.01.bmp`

| 项目 | 值 |
|---|---|
| 尺寸 | 4128 × 4160 |
| 颜色模式 | 1 位图（`0 = 黑 = 笔画`） |
| 网格 | 单元格 16×16，整图 256 列 × 256 行 |
| 偏移 | `dx = 32`，`dy = 64` |
| 寻址 | 码位 `U` 的格子 = 第 `U & 0xFF` 列、第 `U >> 8` 行；像素原点 = `(列×16+32, 行×16+64)` |
| 覆盖 | 全 Unicode BMP，因此 GB2312 的 7445 个字符全部命中 |

## 10. 未覆盖范围

| 范围 | 是否覆盖 |
|---|---|
| ASCII `0x21`–`0x7E` | ✅（来自 `ascii.png`，放大到 16×16） |
| ASCII `0x20`、`0x7F`、控制符 | ⬜ 留空（32 个 `0x00`） |
| GB2312 全部 7445 字符 | ✅（来自 `unifont`，16×16） |
| GB2312 未定义码位（169 个） | ⬜ 填 0 |
| GBK 扩展汉字（区 88–94 之外的部分） | ❌ 未覆盖 |
| GB18030 / 繁体 / 生僻字 | ❌ 未覆盖 |

如需扩展到 GBK，`unifont` 源图本身是够用的（全 BMP），
改 `gen_font.py` 里的 `GB_ROWS` 并补上 GBK 解码即可，但寻址公式需要相应调整。
